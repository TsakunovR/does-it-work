# Аудит готовности к проду: что проверить руками до написания тестов

Ветка «проверь мой продукт / найди баги / можно ли в прод». Здесь не про каркас —
про находки. Порядок сознательный: **сначала дешёвые проверки с высокой отдачей**
(авторизация, утечки, целостность), потом фаззинг спеки, и только потом каркас
регрессионных тестов. Типичное вайб-кодовое приложение сыпется на первом блоке,
и тратить полдня на Page Object'ы до этого — не то, за чем к вам пришли.

Правила игры для всей ветки:

- Проверяем **только тот стенд, который назвал пользователь**. Если он выглядит как
  прод — сначала спросите разрешение на запись/удаление и не создавайте мусор.
- Каждая находка — воспроизводимая: запрос, ответ, ожидание. Скрин или curl,
  а не «мне показалось».
- Формат отчёта — [../examples/prod-readiness-report.md](../examples/prod-readiness-report.md),
  баги в нём — по шаблону [../examples/bug-report.md](../examples/bug-report.md).
- Не чините найденное молча по ходу. Сначала отчёт, объём правок — решение пользователя.

## 0. Префлайт

```bash
python <директория-скилла>/scripts/check_env.py https://stage.example.com --path /health
```

Заодно посмотрите: есть ли `/openapi.json`, `/docs`, `/graphql`, `/metrics`, `/.env`,
`/admin`. Открытые в проде отладочные ручки — это уже находка.

## 1. Авторизация и доступ (самый урожайный блок)

Заведите **двух** пользователей (A и B) и, если есть роли, обычного и админа.

| Проверка | Как | Что плохо |
|---|---|---|
| IDOR по горизонтали | Токеном B запросить/изменить/удалить ресурс пользователя A по его id | 200 вместо 403/404 — **Critical** |
| Эскалация роли при регистрации | `POST /register {"email":..., "role":"admin"}` (и `is_admin`, `isAdmin`, `verified`) | Поле принято и применено — **Critical** (mass assignment) |
| Эскалация через профиль | `PATCH /users/me {"role":"admin"}` | То же — **Critical** |
| Админские ручки под обычным токеном | Все `/admin/*`, `DELETE /users/{id}` | 200/204 — **Critical** |
| Токен без подписи / чужой | Подменить payload JWT, отправить `alg=none`, подписать мусором | Принят — **Critical** |
| Истёкший токен | Дождаться/подделать `exp` в прошлом | Принят — **High** |
| Выход из системы | После logout старый токен | Работает — **Medium** (если нет чёрного списка, отразите в отчёте как известное ограничение) |
| Отсутствие токена | Любая приватная ручка без заголовка | 200 — **Critical**; 403/500 вместо 401 — **Low** |
| Перебор пароля | 20 подряд неверных логинов | Нет ни задержки, ни блокировки — **High** |
| Enumeration пользователей | Логин с несуществующим email vs существующим | Разные тексты/коды ошибок — **Low**, но пишите |

## 2. Утечки данных в ответах

- Пароль/хеш пароля, соль, внутренние токены, `reset_token` — в теле любого ответа: **Critical**.
- Чужие email/телефоны в публичных списках; полный список пользователей без прав: **High**.
- Стек-трейс, SQL-запрос, путь к файлу, версия фреймворка в теле 500: **Medium**
  (в проде — High, это карта для атакующего).
- `Server`, `X-Powered-By` с версиями; отсутствие `Strict-Transport-Security`
  на https: **Low**, одной строкой в отчёте.

## 3. Целостность данных и бизнес-логика

Здесь живут самые дорогие баги вайб-кода: валидация есть на фронте и её нет на бэке.

- **Обход фронтовой валидации**: отправьте напрямую в API то, что форма не даёт ввести —
  отрицательная цена/количество, дата заезда позже даты выезда, бронь в прошлом,
  строка вместо числа, 10 000 символов в имени, отрицательный `limit`/`offset`.
- **Двойная отправка**: два одинаковых POST оплаты/брони подряд (и параллельно) —
  два списания/две брони на один слот = **Critical**.
- **Гонка на дефицитном ресурсе**: 5 параллельных бронирований последнего номера.
  Прошло больше одного — **Critical**.
- **Каскады**: удалите сущность, у которой есть зависимые (пользователь с бронями,
  отель с номерами) — потом запросите зависимые. 500 или «висячие» записи — **High**.
- **Переходы статусов**: отменить уже отменённое, оплатить отменённое, подтвердить
  дважды. Разрешено — **High**.
- **Деньги и округление**: сумма 0, отрицательная, дробная (`0.1 + 0.2`), чужая валюта.
- **Пагинация и сортировка**: `?limit=0`, `?limit=100000`, `?page=-1`,
  сортировка по несуществующему полю. 500 — **Medium**, выгрузка всей базы — **High**.
- **Идемпотентность удаления**: повторный DELETE должен давать 404, а не 500.

## 4. Автоматический фаззинг по спеке (если есть OpenAPI)

Дёшево и находит то, что руками искать долго — недокументированные 500-ки и
расхождения ответов со схемой:

```bash
uv run --with schemathesis schemathesis run https://stage.example.com/openapi.json \
    --checks all --max-failures 20 --report \
    -H "Authorization: Bearer $TOKEN"
```

Что делать с результатом:

- Каждый уникальный **500** — находка (**High**, а если роняет процесс — Critical).
  В отчёт идёт минимальный воспроизводящий запрос из вывода schemathesis, а не весь лог.
- `response_schema_conformance` — расхождение факта со спекой: либо баг кода,
  либо врущая документация. Различить может только пользователь — спросите, не решайте сами.
- Фаззер шумит: сгруппируйте однотипные падения в одну находку («любой `limit` > int32
  роняет `/hotels`»), не выкладывайте 200 строк лога.
- Не гоняйте фаззер по проду без явного разрешения: он создаёт мусорные данные.

Нет OpenAPI — не беда: те же классы проверок из блока 3 руками по 5–10 ключевым ручкам.

## 5. Инфраструктурная гигиена (быстрый проход, всё Low/Medium)

- CORS: `Access-Control-Allow-Origin: *` вместе с `Allow-Credentials: true` — **High**.
- Загрузка файлов: тип и размер не проверяются, файл сохраняется под именем клиента —
  **High**; путь с `../` в имени — **Critical**.
- HTTP не редиректится на HTTPS; секреты в query-параметрах (попадают в логи) — **Medium**.
- `/health` отвечает `ok`, когда БД лежит (проверьте, что он реально что-то щупает) — **Medium**.
- Время ответа ключевых ручек: зафиксируйте p50 из префлайта. Больше 2 с на пустой
  базе — **Medium** и повод сказать «под нагрузкой не проверялось».

## 6. WEB-специфика (если есть UI)

- Приватная страница по прямому URL без логина — редиректит или отдаёт данные?
- Кнопка «удалить» скрыта у обычного юзера, но соответствующий запрос проходит?
- Ошибки бэка на UI: пользователь видит `undefined`/пустой экран/бесконечный спиннер — **Medium**.
- Консоль браузера при прохождении ключевого сценария: ошибки JS — **Medium**, они же
  объясняют часть «странного» поведения.
- Двойной клик по «Оплатить» (см. двойную отправку в блоке 3) — на UI воспроизводится чаще.

## 7. Граница ответственности

Чего этот аудит **не** делает — так и напишите в отчёте, чтобы не создавать ложного
чувства безопасности:

- не нагрузочное тестирование (нет вывода о поведении под трафиком);
- не пентест (нет SQLi/XSS/SSRF-эксплуатации, нет анализа инфраструктуры и зависимостей);
- не аудит кода (смотрим поведение снаружи, если исходники не дали);
- не проверка приватности/соответствия (152-ФЗ, GDPR).

## 8. Что остаётся пользователю

Находки — половина работы. Вторая половина: превратить подтверждённые баги в тесты
(`xfail(reason="Баг API: ...", strict=True)` — тест сам просигналит XPASS, когда починят)
и оставить каркас регрессии по шагам 1–5 SKILL.md. Приоритет покрытия — ровно те места,
где нашлись Critical/High: там баги уже доказали, что водятся.
